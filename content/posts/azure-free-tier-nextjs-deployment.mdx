Azure Static Web Apps (SWA) has a genuinely good free tier that supports modern Next.js features. But the documentation is scattered, the default configs have gotchas, and the error messages aren't always helpful. This guide covers the exact setup that works.

## What Azure Static Web Apps Free Tier Gives You

Before we start: know what you're getting.

| Feature | Free Tier |
|---------|-----------|
| Custom domains | 2 |
| SSL certificates | Yes (auto) |
| Bandwidth | 100 GB/month |
| Storage | 0.5 GB |
| API (Azure Functions) calls | 6 million/month |
| Build minutes | 250/month |
| SSR/Server Actions | Yes (via managed Functions) |
| Environments (staging) | 3 |

For a blog, newsletter site, or small app: this is plenty. For anything with meaningful traffic or complex serverless needs, you'll need the Standard tier ($9/month).

## The Deployment Architecture

When you deploy a Next.js app to SWA, here's what happens:

- **Static assets** (CSS, JS, images) → served from Azure CDN globally
- **Server Components and dynamic routes** → run as Azure Functions (Managed Functions)
- **API routes** → also Azure Functions
- **Server Actions** → Azure Functions

The SWA CLI handles the Next.js → Azure Functions compilation automatically. You don't need to configure Functions manually.

## Step 1: Prepare Your Next.js App

Your `next.config.ts` needs no special changes for SWA. The SWA build process handles everything. Just ensure you're on Next.js 14+ (App Router works fully).

One important note: SWA uses Node.js 20 LTS. Make sure your `package.json` specifies this if you have runtime-specific code:

```json
{
  "engines": {
    "node": ">=20"
  }
}
```

## Step 2: Create the Azure Static Web App

**Option A: Via Azure Portal**

1. Go to [portal.azure.com](https://portal.azure.com)
2. Create Resource → Static Web App
3. Free plan, East US region (or closest to your users)
4. Connect to GitHub (recommended) or use manual deployment
5. Build details: choose "Next.js" from the dropdown
6. Azure auto-detects your app root and output folder

**Option B: Via Azure CLI (faster)**

```bash
# Install Azure CLI
winget install Microsoft.AzureCLI

# Login
az login

# Create resource group
az group create --name blog-rg --location eastus

# Create Static Web App
az staticwebapp create \
  --name devpulse-blog \
  --resource-group blog-rg \
  --source https://github.com/yourusername/your-repo \
  --branch main \
  --app-location "/" \
  --output-location ".next" \
  --login-with-github
```

## Step 3: Configure the Build

Create `staticwebapp.config.json` in your project root:

```json
{
  "platform": {
    "apiRuntime": "node:20"
  },
  "navigationFallback": {
    "rewrite": "/index.html",
    "exclude": ["/api/*", "/_next/*", "/images/*"]
  },
  "routes": [
    {
      "route": "/feed.xml",
      "headers": {
        "content-type": "application/xml"
      }
    },
    {
      "route": "/sitemap.xml",
      "headers": {
        "content-type": "application/xml"
      }
    }
  ],
  "globalHeaders": {
    "X-Content-Type-Options": "nosniff",
    "X-Frame-Options": "DENY",
    "X-XSS-Protection": "1; mode=block",
    "Referrer-Policy": "strict-origin-when-cross-origin"
  },
  "mimeTypes": {
    ".xml": "application/xml"
  }
}
```

## Step 4: GitHub Actions (Auto-generated, but Here's What It Does)

When you connect GitHub, Azure creates a workflow file automatically. Here's the key part:

```yaml
# .github/workflows/azure-static-web-apps.yml
name: Azure Static Web Apps CI/CD

on:
  push:
    branches:
      - main
  pull_request:
    types: [opened, synchronize, reopened, closed]
    branches:
      - main

jobs:
  build_and_deploy_job:
    runs-on: ubuntu-latest
    name: Build and Deploy Job
    steps:
      - uses: actions/checkout@v3
        with:
          submodules: true

      - name: Build And Deploy
        uses: Azure/static-web-apps-deploy@v1
        with:
          azure_static_web_apps_api_token: ${{ secrets.AZURE_STATIC_WEB_APPS_API_TOKEN }}
          repo_token: ${{ secrets.GITHUB_TOKEN }}
          action: "upload"
          app_location: "/"
          api_location: ""
          output_location: ".next"
        env:
          NODE_VERSION: "20"
          # Add your env vars here:
          NEXT_PUBLIC_SITE_URL: "https://your-app.azurestaticapps.net"
          RESEND_API_KEY: ${{ secrets.RESEND_API_KEY }}
          NEXT_PUBLIC_ADSENSE_ID: ${{ secrets.NEXT_PUBLIC_ADSENSE_ID }}
```

**Important**: Add your secrets in GitHub: Settings → Secrets and variables → Actions.

## Step 5: Environment Variables

SWA has two places for env vars:

**Build-time variables** (NEXT_PUBLIC_* and those needed during `next build`): Set in the GitHub Actions workflow or in SWA portal under Configuration → Application settings.

**Runtime variables** (API route secrets, database URLs): Set in Azure Portal → Your Static Web App → Configuration → Application settings. These are injected as environment variables into the Azure Functions runtime.

```
RESEND_API_KEY=re_xxxxx
RESEND_AUDIENCE_ID=xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx
NEXT_PUBLIC_SITE_URL=https://devpulse.azurestaticapps.net
NEXT_PUBLIC_ADSENSE_ID=ca-pub-xxxxxxxxxxxxxxxx
```

## The Gotchas (Learn From My Pain)

**Gotcha 1: Dynamic routes need `generateStaticParams` or `force-dynamic`**

SWA pre-builds your app. Dynamic routes without `generateStaticParams` will 404 unless you explicitly mark them as dynamic:

```typescript
// Option A: Generate all params at build time
export async function generateStaticParams() {
  const posts = getAllPosts();
  return posts.map(p => ({ slug: p.slug }));
}

// Option B: Force server-side rendering
export const dynamic = 'force-dynamic';
```

For a blog where you add posts via Git, Option A is usually right. For truly dynamic routes (user-generated content), use Option B.

**Gotcha 2: `next/image` needs a domain allowlist**

```typescript
// next.config.ts
const nextConfig = {
  images: {
    remotePatterns: [
      {
        protocol: 'https',
        hostname: '**.azurestaticapps.net',
      },
    ],
  },
};
```

**Gotcha 3: File-based content needs to be in the repo**

If your blog posts are in `content/posts/*.mdx`, they need to be committed to Git. SWA builds from source — it doesn't have access to your local filesystem. This is obvious in hindsight but trips people up.

**Gotcha 4: The SWA emulator is your friend**

Before deploying, test locally with:

```bash
npm install -g @azure/static-web-apps-cli
swa start http://localhost:3000 --run "npm run dev"
```

This emulates the SWA routing, authentication, and API behavior locally. Issues that only appear in production are usually caught here.

## Custom Domain Setup

Once deployed, adding a custom domain is free and takes about 5 minutes:

1. Azure Portal → Your SWA → Custom domains → Add
2. Add your domain name
3. Copy the CNAME or TXT record
4. Add to your DNS provider (Cloudflare, Route 53, etc.)
5. Azure provisions an SSL certificate automatically via Let's Encrypt

With Cloudflare in front (free), you get additional caching and DDoS protection on top of Azure CDN.

## Performance in Production

Real numbers from a Next.js blog on SWA free tier (low traffic, US East):

| Route | TTFB | FCP | LCP |
|-------|------|-----|-----|
| Homepage (SSG) | 45ms | 0.7s | 1.1s |
| Blog post (SSG) | 52ms | 0.8s | 1.3s |
| Tag page (SSR) | 180ms | 1.1s | 1.8s |
| API route | 145ms | — | — |

Static pages served from CDN are fast. Server-rendered routes are slower — those Azure Functions have cold start latency of 150-300ms. For a blog where most content is pre-rendered, this is a non-issue.

If you need consistently fast SSR, SWA Standard tier reduces cold starts. At $9/month, it's worth it once you have meaningful traffic.

## Free Tier Limitations to Watch

- **No background jobs** — scheduled tasks need Azure Functions separately or a free-tier external service
- **No WebSockets** — use SSE or polling instead
- **0.5 GB storage** — for a static blog this is fine; for user uploads you need Blob Storage
- **250 build minutes/month** — if you're rebuilding for every commit on a monorepo, watch this

For most blogs and small apps, you won't hit these limits for months. The free tier is genuinely useful.
