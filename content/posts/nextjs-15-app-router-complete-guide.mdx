Next.js 15 shipped with a list of changes long enough to confuse even experienced developers. After building several production apps on it, here's what you actually need to know — stripped of the marketing fluff.

## The Caching Reversal That Broke Everyone's Apps

Let's start with the change that caused the most breakage: **fetch requests are no longer cached by default**.

In Next.js 14, this would cache the response indefinitely:
```typescript
const data = await fetch('https://api.example.com/posts');
```

In Next.js 15, the same code does NOT cache. You have to opt in explicitly:
```typescript
// Cache indefinitely (equivalent to old default)
const data = await fetch('https://api.example.com/posts', {
  cache: 'force-cache'
});

// Cache for 60 seconds
const data = await fetch('https://api.example.com/posts', {
  next: { revalidate: 60 }
});

// Never cache (also the new default, so this is redundant)
const data = await fetch('https://api.example.com/posts', {
  cache: 'no-store'
});
```

This was a breaking change that burned a lot of people. If you're migrating from 14, audit every `fetch` call.

## Server Components: The Mental Model

Server Components are still the most misunderstood feature in Next.js. Here's the model that finally clicked for me.

**Server Components run once, on the server, per request.** They have no event handlers, no state, no browser APIs. What they do have: direct database access, filesystem access, and zero client-side JavaScript.

```typescript
// app/blog/page.tsx — Server Component by default
import { db } from '@/lib/db';

export default async function BlogPage() {
  // Direct DB query — no API layer needed
  const posts = await db.post.findMany({
    orderBy: { createdAt: 'desc' },
    take: 10,
  });

  return (
    <ul>
      {posts.map(post => (
        <li key={post.id}>{post.title}</li>
      ))}
    </ul>
  );
}
```

**Client Components get the `'use client'` directive.** They run in the browser and can use hooks, event handlers, and browser APIs. They still render on the server for the initial HTML (SSR), but they also hydrate on the client.

```typescript
'use client';

import { useState } from 'react';

export function LikeButton({ postId }: { postId: string }) {
  const [liked, setLiked] = useState(false);
  return (
    <button onClick={() => setLiked(!liked)}>
      {liked ? '❤️' : '🤍'}
    </button>
  );
}
```

The rule: **push `'use client'` as deep in the component tree as possible**. A Server Component can import a Client Component, but not vice versa (directly — you can pass Server Components as children to Client Components).

## Server Actions: The API Layer Killer

Server Actions let you write server-side mutations that get called directly from client-side forms and event handlers. No manual API routes, no fetch calls, no serialization boilerplate.

```typescript
// app/actions/posts.ts
'use server';

import { db } from '@/lib/db';
import { revalidatePath } from 'next/cache';
import { z } from 'zod';

const CreatePostSchema = z.object({
  title: z.string().min(1).max(200),
  content: z.string().min(1),
});

export async function createPost(formData: FormData) {
  const parsed = CreatePostSchema.safeParse({
    title: formData.get('title'),
    content: formData.get('content'),
  });

  if (!parsed.success) {
    return { error: parsed.error.flatten() };
  }

  await db.post.create({ data: parsed.data });
  revalidatePath('/blog');
  return { success: true };
}
```

Using this in a form is dead simple:

```typescript
'use client';
import { createPost } from '@/app/actions/posts';

export function NewPostForm() {
  return (
    <form action={createPost}>
      <input name="title" placeholder="Title" required />
      <textarea name="content" placeholder="Content" required />
      <button type="submit">Publish</button>
    </form>
  );
}
```

The `'use server'` directive marks functions as server-only. Next.js handles the network call behind the scenes. You get automatic CSRF protection, type safety, and no API route boilerplate.

## generateMetadata: Dynamic SEO Done Right

Static metadata is simple. Dynamic metadata — where the title and description depend on fetched data — requires `generateMetadata`:

```typescript
// app/blog/[slug]/page.tsx
import { getPostBySlug } from '@/lib/posts';
import type { Metadata } from 'next';

interface Props {
  params: Promise<{ slug: string }>;
}

export async function generateMetadata({ params }: Props): Promise<Metadata> {
  const { slug } = await params; // params is now async in Next.js 15
  const post = await getPostBySlug(slug);

  if (!post) {
    return { title: 'Post Not Found' };
  }

  return {
    title: post.title,
    description: post.excerpt,
    openGraph: {
      title: post.title,
      description: post.excerpt,
      type: 'article',
      publishedTime: post.date,
    },
  };
}
```

Note: in Next.js 15, `params` and `searchParams` are now **Promises**. This catches a lot of developers who copy-paste code from Next.js 14 examples. Always `await params`.

## Partial Prerendering (PPR)

PPR is one of the more interesting rendering innovations in Next.js 15. It lets you mix static and dynamic content in a single route — without SSR for the whole page.

```typescript
// app/blog/[slug]/page.tsx
import { Suspense } from 'react';
import { PostHeader } from './PostHeader'; // Static — prerendered
import { Comments } from './Comments';     // Dynamic — rendered on request

export default function PostPage({ params }) {
  return (
    <>
      {/* Rendered at build time — instantly available */}
      <PostHeader slug={params.slug} />

      {/* Rendered on each request — shows skeleton during load */}
      <Suspense fallback={<CommentsSkeleton />}>
        <Comments postId={params.slug} />
      </Suspense>
    </>
  );
}
```

With PPR enabled in `next.config.ts`, the static shell (header, layout, above-the-fold content) is served from the CDN edge immediately. Dynamic parts stream in after. Real-world result: dramatically better Time to First Byte for content-heavy pages.

Enable it:
```typescript
// next.config.ts
const nextConfig = {
  experimental: {
    ppr: 'incremental', // opt-in per route, or true for all
  },
};
```

## The Loading and Error Convention

Next.js uses special files to handle loading and error states at the route level:

```
app/
  blog/
    loading.tsx    ← Shown while page.tsx data fetches
    error.tsx      ← Shown if page.tsx throws
    page.tsx
```

```typescript
// app/blog/loading.tsx
export default function BlogLoading() {
  return (
    <div className="grid grid-cols-3 gap-5">
      {Array.from({ length: 6 }).map((_, i) => (
        <div key={i} className="h-48 bg-muted rounded-lg animate-pulse" />
      ))}
    </div>
  );
}
```

```typescript
// app/blog/error.tsx
'use client'; // Error components must be Client Components

import { useEffect } from 'react';

export default function BlogError({
  error,
  reset,
}: {
  error: Error & { digest?: string };
  reset: () => void;
}) {
  useEffect(() => {
    console.error(error);
  }, [error]);

  return (
    <div>
      <h2>Something went wrong loading the blog.</h2>
      <button onClick={reset}>Try again</button>
    </div>
  );
}
```

## When to Use What

Here's the decision matrix I use for every component:

| Needs | Use |
|-------|-----|
| Data fetching, DB queries | Server Component |
| Static content | Server Component |
| Event handlers, onClick | Client Component |
| useState, useEffect | Client Component |
| Form with mutation | Server Action |
| Complex API logic | Route Handler (`route.ts`) |
| Layout shared across pages | `layout.tsx` |
| Loading skeleton | `loading.tsx` |

## Performance Numbers

Real benchmark from a blog migration from Pages Router to App Router (Next.js 15):

| Metric | Before (Pages Router) | After (App Router) |
|--------|----------------------|-------------------|
| FCP | 1.8s | 0.9s |
| LCP | 2.4s | 1.3s |
| JS bundle (initial) | 245 KB | 87 KB |
| Lighthouse Performance | 74 | 96 |

The JS bundle reduction is the biggest win. Server Components send zero JavaScript to the client. For a content-heavy blog with mostly static content, this is transformative.

App Router is no longer experimental and has no real downsides for new projects. If you're starting something new in 2026, App Router is the only answer.
